# `jvs_kc_wbc_trajfollow.launch.py` 运行流程

该 launch 的主流程是：**重置并校验机器人 → 准备碰撞输入 → 启动 KC-WBC → 进行 50 Hz 闭环轨迹跟踪**。groundtruth 等待网格提取成功；LiDAR 先启动控制器接收两路点云，地图就绪后才开始运动。详见 [实时双 LiDAR 接口](LIDAR_WBC.md)。

> 前置条件：`jvs_kc_wbc_isaac.launch.py` 已经启动。两个 launch 必须使用相同的 `ROS_DOMAIN_ID`、`stage_view` 和出生位姿。

`trajectory_file` 同时支持完整轨迹 `shot_comboN.json` 和纯动作序列
`shot_comboN_actions.json`。后者在启动相机坐标系中保留各动作样本，由
`CameraTrajectory` 运行时生成 C2 最小 jerk 衔接，再交给相同的 WBC/MPC。
输入文件没有全局衔接时间戳；生成后的 `execution_shots`、衔接参数与时长
保存在 `reference.json`。精度门槛仅评估动作区间，衔接仍参与全程安全与命令
连续性检查。格式、公式和复现命令见
[Combo 动作序列与自动衔接](STAGE3_KC_WBC.md#combo-动作序列与自动衔接2026-10-02)。

## 执行 combo 时涉及的节点与进程

当前 KC-WBC combo 运行由两个 launch 进程组共同完成。真正参与控制闭环的 ROS 节点很少；网格提取器和异步预测 worker 是普通子进程，不是 ROS 节点。

| 节点或进程 | 生命周期 | 作用 |
|---|---|---|
| Isaac Sim OmniGraph ROS 2 Bridge | Isaac 场景运行期间常驻 | 发布 `/clock`、`/joint_states`、`/base_controller/odom`，订阅 `/isaac_joint_commands` 并驱动机器人 |
| `/jvs_isaac_reset_server` | Isaac 场景运行期间常驻 | `jvs_simview_isaac.py` 内嵌的 rclpy 节点，提供 `/jvs/reset_robot` 服务，恢复出生位姿、关节状态和速度 |
| `/jvs_isaac_reset_client` | 每次 trajfollow 启动时临时运行 | 调用 reset 服务，发布零速/零位保持命令，并用 joint state 与 odom 连续验证复位结果；成功后退出 |
| `extract_usda_collision_mesh.py` | reset 成功后临时运行 | 普通进程；复用或生成 KC 碰撞网格，成功退出后才允许启动 WBC |
| `/whole_body_controller` | 网格就绪后常驻 | combo 轨迹采样、路径时钟、预测规划、50 Hz 执行 QP、安全认证、命令发布、诊断和指标记录 |
| Async preview worker | WBC 内部子进程 | 计算 3.2 秒预测窗的障碍感知全身速度计划，不直接发布或订阅 ROS 话题 |
| `/wbc/shot_context` 的外部发布者 | 可选，当前 launch 不创建 | 可在运行时覆盖运镜上下文；未连接时直接使用所选轨迹（例如 `shot_combo1.json`）中的 shot 定义 |

`jvs_kc_wbc_isaac.launch.py` 显式关闭了旧的 `isaac_command_adapter` 和 `jvs_follow_traj`。因此 combo 运行时，`/isaac_joint_commands` 的所有权按阶段切换：复位阶段由 reset client 独占，reset client 退出后由 WBC 独占。

```text
第一个 launch：jvs_kc_wbc_isaac.launch.py

## 隐含状态机总览

程序没有集中定义一个状态枚举。下面的状态由 launch 事件和 WBC 内部变量共同形成：

- `trajectory is None` 区分“尚未建立轨迹”和“已经进入轨迹生命周期”。
- `elapsed < 0` 表示机械臂准备；`elapsed >= 0` 表示 combo 路径时钟已经启动。
- `failure` 非空会让后续控制周期持续选择制动 QP。
- `emergency=True` 后只发布零命令，不再尝试正常跟踪。
- `completed=True` 表示结果已经落盘，但节点仍保持运行。
- `pending`、`plan` 和 `planner_braking` 形成独立的异步预测规划子状态机。

## combo 轨迹内部状态机

当前 `shot_combo1.json`（原 `shot_combo_reachable.json`）的总路径时间为 58 秒，由 Orbit、Pan 和 MoveOut 三个 shot 组成。这里的时间是自适应 `ShotClock` 的路径时间，并非固定的真实运行时间：跟踪误差、底盘朝向误差或机械臂伸展过大时，路径时钟会减速，因此实际执行可能明显长于 58 秒。其余编号组合有各自的动作顺序和时间边界，下图仅对应 combo1。

                       ▼
┌─────────────────────────────────────────────┐
│ C4：PAN → MOVEOUT TRANSITION                │
│ 路径时间 [38, 42) s                         │
│ 相机参考静止；为 MoveOut 调整底盘和机械臂   │
│                                             │
│ t=40 s：shot 标签由 pan 切换为 moveout      │
│ t=39～41 s：运镜权重平滑混合                │
└──────────────────────┬──────────────────────┘
                       │ t = 42 s
                       ▼
┌─────────────────────────────────────────────┐
│ C5：MOVEOUT_MOTION                          │
│ 路径时间 [42, 56) s                         │
│ 保持 Kid 主体锁定并执行约 0.7 m 后拉        │
└──────────────────────┬──────────────────────┘
                       │ t = 56 s
                       ▼
┌─────────────────────────────────────────────┐
│ C6：FINAL_HOLD                              │
│ 路径时间 [56, 58] s                         │
│ 保持 combo 最终相机位姿                     │
└──────────────────────┬──────────────────────┘
                       │ t > 58 s
                       ▼
              WBC 的 ENDPOINT_HOLD
```

需要区分两个同时存在的状态维度：`shot_context()` 在 22 秒和 40 秒切换 shot 标签，而 `transition()` 使用 `[20,24)` 和 `[38,42)` 两个静止窗口。因此控制器在一部分 Orbit/Pan 标签时间内已经进入衔接准备状态；它并不是简单地在 shot 边界瞬间切换控制目标。

衔接内的停车方向和到达阶段由实际执行状态提交一次，底盘目标在窗口两端以及
下一动作开始处平滑混合。后台预测仅提供候选计划和姿态评分，不覆盖已经提交的
执行分支；低速姿态偏好从实测关节初始化，避免半圈转向处改变 IK 分支。
停留期间相机任务优先，底盘准备可使实际执行时间加长。
限位一致性、噪声触发跳变和八条实际仿真的核查数据见
[衔接抖动核查与修复](STAGE3_KC_WBC.md#combo-衔接抖动核查与修复2026-10-02)。

## 异步预测规划子状态机

异步规划包含两个并行状态维度：worker 是否正在计算，以及执行 QP 当前是否持有可用计划。提交新规划时，现有计划不会立刻失效。
